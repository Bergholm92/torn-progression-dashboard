# Codex migration plan — 2026-10-15

## Outcome
Use Codex for autonomous multi-step development while preserving the existing live Torn dashboard and Supabase deployment. Do not confuse moving development to Codex with moving the running infrastructure away from Supabase.

## Confirmed starting point
- This repository is PUBLIC and mainly contains the frontend.
- Production Supabase contains 3 deployed Edge Functions, 42 tables, 137 analytics views and 22 SQL functions.
- Several recommendations are generated by database views. Migrating only the Edge Functions is NOT a complete migration.
- Preserve the live system until source/production parity is tested.

## Phase 1 — public frontend (safe to do now)
1. Add `AGENTS.md`, architecture and handoff documentation, and frontend CI.
2. Review `QUALITY_RECOVERY_PLAN.md` and turn its open items into executable regression tests.
3. Use Codex Cloud with this repository; start with a branch/PR and run `node tests/smoke.cjs`.

## Phase 2 — PRIVATE backend source control (requires GitHub setup)
1. Create a separate **private** GitHub repository, suggested name `torn-progression-core`. Keep this existing repository public so the current static dashboard remains available.
2. Connect the private repository to the same Codex Cloud environment or create a suitable separate environment.
3. Use the official Supabase CLI in a trusted environment: initialize a local `supabase/` directory, authenticate securely, and link project `sdczpggpsrikncdzpsie`.
4. Download ALL THREE current production Edge Functions (`torn-collector`, `torn-dashboard`, `torn-brief-delivery`) into `supabase/functions/<name>/`. Compare source to live versions; do not rewrite or redeploy while establishing the baseline.
5. Export the complete schema, including 137 analytics views, 22 functions, RLS policies, grants, triggers and schedules, using the supported schema/migration workflow (`supabase db pull` and schema inspection). **Do not** hand-write a fake baseline migration or treat a list of table names as a schema backup.
6. Review generated SQL for hidden secrets, private user data, SECURITY DEFINER and grants before committing. Keep secrets out of Git and rotate any inadvertently exposed secret.
7. Create an exact baseline tag and reproducibility report. Check that a fresh local/staging project can initialize without production data.
8. Add a controlled deployment workflow. Staging first; production only after explicit approval and a successful quality gate.

## Phase 3 — quality and operations
- Add tests for education prerequisites, current job/company facts, Cracking vs Disposal crime advice, merit decisions, Balboa/specialist gym eligibility, battle-stat projections, historical retention, freshness, and conflicts.
- Compare actual API responses with expected behavior using **sanitized fixtures**, not live secret credentials in CI.
- Introduce explicit statuses: PASS, FAIL, REVIEW, NO DATA, BLOCKED. Never equate a successful API call with sound advice.
- Add GitHub Actions checks and require an approved PR to deploy.
- Review email delivery's current preflight/idempotency limitation before any unattended sending.
